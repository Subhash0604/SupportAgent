Problem Framing: What "Good" Means for AmazonHelpBuilding automated triage for Twitter customer support is deceptively tricky. Unlike private email ticketing, Twitter/X is public, hostile, fast-paced, and strictly character-limited. A customer tweeting at @AmazonHelp is usually already annoyed because self-service failed them.What "Good" Actually Means HereZero Public PII/Financial Leakage: If a user posts an order ID, credit card digits, or email address, the bot must never repeat that information or continue troubleshooting on the public thread. "Good" means immediately locking down the thread and taking the customer to private authentication (Direct Message or official help portal).High Escalation Recall Over Precision: In retail operations, a false positive (sending a routine query to a human) costs a few extra minutes of agent time. A false negative (auto-replying with a cheerful generic message to someone whose account got hijacked or whose package was stolen) triggers viral public escalation, regulatory complaints, and churn. We tuned the system to aggressively favor human escalation on ambiguity.Succinct, Empathetic, Policy-Accurate Drafts: Replies must be under 280 characters, mirror the friendly de-escalation tone of authentic AmazonHelp representatives, and never make ungrounded promises (like "I've just refunded your $50" or "Your replacement will arrive in 2 hours").What We Deliberately Chose NOT to BuildAutonomous In-Channel Account Transactions: We do not automatically trigger refunds, cancellations, or password resets via the Twitter API. Public social channels have zero cryptographically verified identity. Triggering financial actions from unauthenticated tweets is an unacceptable attack vector for social engineering.Granular 50+ Intent Taxonomies: Academic benchmarks like Banking77 classify dozens of hyper-specific intents. In practice, tiered support teams only care about the immediate routing destination. We condensed the taxonomy down to 6 operational buckets (shipping_status, returns_refunds, damaged_stolen, account_access, general_complaint, out_of_scope).Multi-Turn Chatbots on Public Threads: Long Twitter back-and-forth threads look sloppy and expose customer grievances publicly. We built a single-turn resolution router designed to deflect or push directly to secure DM.2. Golden Evaluation Set MethodologyTo ground our benchmarks in real customer behavior rather than synthetic LLM text, we constructed a hand-labeled golden test set of 200 examples (backend/data/golden_eval.jsonl).Sampling StrategyWe stratified sampling from the 3M+ Kaggle Customer Support on Twitter dataset (twcs.csv) targeting the @AmazonHelp handle:60% Core Operational Queries: Common queries around tracking, Prime delivery delays, returns, and digital subscriptions (Prime Video/Kindle).20% High-Risk Security & Legal Cases: Account takeovers, suspicious unauthorized charges, stolen doorstep packages, and threats of litigation.10% Sarcastic / High-Frustration Complaints: Tweets where surface sentiment contains positive words ("Great job Amazon!") but expresses anger ("Great job delivering my package to the neighbor's roof!").10% Noise & Out-of-Scope Data: Spam bots, empty replies ("thanks"), and questions about competing platforms (Netflix, Walmart).Labeling ProtocolI hand-annotated every record across four target fields:true_intent: One of the 6 core operational categories.true_routing: AUTO_REPLY (safe to answer) vs. ESCALATE_TO_HUMAN (requires manual review or secure DM).ground_truth_key_facts: Explicit checklist items the drafted response must contain (e.g., "Must prompt for DM", "Must not promise refund publicly").human_tone_score & human_grounding_score: 1–5 ordinal rubric baseline used to calibrate the automated LLM judge.3. Evaluation Harness & Human-Judge AgreementTo run benchmarks efficiently without hand-evaluating every model iteration, we implemented an LLM-as-a-judge harness (backend/eval/llm_judge.py) using gemini-2.5-flash with strict JSON schema outputs.The RubricTone (1–5): 1 = dismissive/combative; 3 = purely robotic/unhelpful; 5 = empathetic, professional, within Twitter character limits.Policy Grounding (1–5): 1 = promises unauthorized refunds or contradicts policy; 3 = vague guidance; 5 = strictly adheres to retail protocol.Binary Acceptance (0 or 1): 1 = acceptable to send to a customer right now; 0 = rejected due to tone or policy flaws.Proving Human-Judge Alignment (Cohen's Kappa)We ran a blind calibration study on a 30-sample subset scored independently by the author and the LLM judge:Binary Decision Agreement ($\kappa$): 0.82 (Unweighted Cohen's Kappa, indicating substantial-to-near-perfect alignment).Tone Quadratic Weighted $\kappa$: 0.78Grounding Quadratic Weighted $\kappa$: 0.84Because the judge achieved $\kappa > 0.75$ across both ordinal rubrics and the binary acceptance decision, we can trust the automated benchmark runs to reflect real human QA standards.4. Failure Analysis: Top 5 Failure ModesLooking at where the RAG agent stumbled during benchmark runs reveals where pure text pipelines hit their limits:1. Multimodal Damage ClaimsIncoming Tweet: "My order arrived today. Unbelievable. [image_01.jpg attached]"What Happened: The model classified this as shipping_status because the text only mentioned "arrived today."Why It Failed: The text contains zero complaint tokens. The actual complaint (a crushed box) is locked inside the attached image.Fix: Connect Gemini's vision endpoint to inspect image attachments whenever tweet text is sparse.2. Compound Multi-Intent InquiriesIncoming Tweet: "My package was 4 days late AND you charged me $14.99 twice for Prime this month."What Happened: Classified as shipping_status, and the draft only addressed the package delay, ignoring the double charge.Why It Failed: The classifier forces a single discrete intent label. When two distinct problems are raised in one sentence, secondary intents get dropped.Fix: Move to multi-label intent prediction and synthesize a draft addressing each detected component.3. Sarcasm with Surface-Positive SentimentIncoming Tweet: "Huge round of applause to Amazon for throwing my laptop over the fence in the rain! Truly outstanding."What Happened: The zero-shot step marked confidence at 0.71 and proposed an AUTO_REPLY thanking the customer. The regex layer did not trigger because no PII was present.Why It Failed: Surface praise words ("applause", "outstanding") threw off the prompt's sentiment extraction.Fix: Add dedicated few-shot exemplars in Qdrant specifically illustrating sarcastic delivery complaints.4. Over-Triggering PII on Plain Numeric SequencesIncoming Tweet: "I've been a Prime member for 12 years and tried 3 times to change my password!"What Happened: Routed to ESCALATE_TO_HUMAN citing PII detection.Why It Failed: A naive regex looking for digit patterns misidentified "12 ... 3" as a fragmented account identifier.Fix: Replace crude digit regexes with a targeted regex requiring the exact Amazon order number schema (\d{3}-\d{7}-\d{7}) or use lightweight Spacy NER.5. Conversational Fragment Loss (Thread Truncation)Incoming Tweet: "No, I already told you guys that didn't work."What Happened: Classified as out_of_scope with low confidence.Why It Failed: Kaggle data occasionally contains standalone tweets stripped of their parent conversational context (in_reply_to_status_id). Isolated replies are unclassifiable.Fix: In production, wrap the Twitter API call to pull the previous 2 turns of the thread before passing the payload to FastAPI.6. "What Is Misleading About My Headline Number?"Every ML evaluation has structural blind spots. Here is what our 0.88 Macro F1 and 95% Recall numbers hide:Synthetic Bias in the Escalation Test Slice: To properly benchmark safety, 20% of our golden evaluation set contains explicit edge cases (stolen boxes, credit card numbers, fraud). In real Twitter traffic, raw PII leaks appear in roughly 2–4% of inbound tweets. Our reported recall is tested on an artificially dense set of safety hazards.The "Canned DM" Shortcut: In the historical Kaggle dataset, human Amazon agents frequently send a stock canned reply: "We'd like to look into this. Please reach out via DM." Because that generic reply fits almost any problem, an LLM judge evaluating "policy grounding" gives high scores to replies that might actually feel dismissive to a customer looking for a direct answer.Survival Bias of Twitter Complaints: Customers who tweet at Amazon represent a skewed demographic—people who are more vocal, tech-savvy, or frustrated than average customers who resolve issues via the mobile app. The model's high score reflects performance on this specific subset, not on all Amazon customer touchpoints.7. What I Would Do Next with One More WeekMulti-Turn Thread Context Buffer: Use Redis to track thread conversations across tweet IDs so the agent remembers previous suggestions and customer replies.Direct Message Hand-off Webhook: Integrate a backend webhook that passes context to human Zendesk/Salesforce agent consoles when ESCALATE_TO_HUMAN triggers.Dynamic Few-Shot Reranking (MMR): Implement Maximal Marginal Relevance in Qdrant retrieval to eliminate redundant exemplar replies and expose the LLM to diverse response styles.Automated Redaction Pre-Processor: Instead of solely escalating when PII is detected, redact the sensitive snippet ([REDACTED_ORDER_ID]) before feeding the text to the model to reduce token exposure.8. Decision LogA chronological breakdown of technical trade-offs made during development:Polars over Pandas: We used Polars lazy evaluation (pl.scan_csv) to parse the 492 MB twcs.csv file. It completed filtering down to 3,000 clean pairs in 3.8 seconds, whereas Pandas consumed 2.4 GB of RAM and took over 20 seconds.Local Embedded Qdrant over Docker: We used local disk storage (QdrantClient(path=...)) rather than running a containerized Qdrant instance. This removes Docker Desktop networking overhead and makes the repo clone-and-runnable in minutes.Hard Regex Interlock Before LLM Inference: We evaluate regex checks for credit cards and order IDs before calling the model. Running safety rules in deterministic code guarantees compliance regardless of model hallucinations or temperature variations.JSON Schema Enforcement over Raw Prompting: Using Gemini's response_schema eliminates unstructured markdown blocks and JSON syntax crashes, preventing parser breaks in production.Prioritizing Escalation Recall over Precision: We deliberately tuned our prompt and confidence gating to bias toward ESCALATE_TO_HUMAN. A false escalation costs minor agent time; a missed angry customer causes public relations churn.6 Coarse Intents over 50 Fine-Grained Classes: Support operations need to know where to send a ticket (Logistics, Fraud, Billing, or Returns), not nuanced linguistic labels. Coarse intent models yield much higher operational reliability.FastAPI Backend with Direct Pydantic Schemas: Keeping all validation and inference within FastAPI avoids cross-service serialization overhead and keeps the API surface clean.Next.js App Router for the Workbench: Built the triage testing interface in Next.js 14 with Tailwind CSS, giving internal QA reviewers a fast, visual way to inspect similarity scores and latency metrics.Rate-Limit Resilient Benchmark Harness: Added automated backoff (delay = 15.0) in the benchmark runner to handle API rate limits smoothly without crashing long evaluation runs.Excluding Raw CSV from Git History: Kept the 492 MB raw dataset out of Git history and used a lightweight, high-signal golden set (golden_eval.jsonl) for tests, keeping the repository fast to clone.
